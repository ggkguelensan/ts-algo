# Цель и целевое устройство ts-algo

**ts-algo — небольшие синхронные операции и статические индексы для прикладных
выборок над ссылками на отдельно хранящиеся сущности.** Основной пользователь —
разработчик каталогов, расписаний и редакторов, который уже использует Map/Array
и хочет совместить внешний источник данных, структурные метаданные и обычные
преобразования без собственного движка запросов.

Этот документ — авторитетный выбор направления по результатам исследования.
[Эксперименты](../experiments/goal/research.md) содержат методы и воспроизводимые
доказательства; [аудит исследования](../experiments/goal/completion.md) связывает их
с исследовательским заданием. [Аудит публичной миграции](../experiments/goal/migration-audit.md)
проверяет перенос выбранных решений в пакет. Здесь описаны выбранные контракты и ход переноса в публичный API.
Исследовательские прототипы остаются вне поставки. Текущий API показан в README.
Source/collect и Source-overload sorted реализованы; time/ranges/tree/dependencies/spatial
и queue/deque/lists/diff доступны отдельными импортами. Корень содержит только ядро.
Сценарии проверены через установленный пакет; типы, память, runtime и гранулярность
импорта имеют отдельные измерения. Пакет остаётся private и не опубликован.

## Почему библиотека заслуживает существования

Полезно сочетание трёх решений: разрешение ссылки в сущность, отдельный индекс
метаданных и небольшая выборка с фильтром/проекцией. Оно убирает повторяемую
связующую логику между внешним Map и предметным поиском, сохраняет тип ключа и
позволяет выбирать только нужные функции. Для времени дополнительно полезны
явные полуоткрытые интервалы, свободные промежутки и ограничения ёмкости.

Исследование не установило превосходства над прямыми циклами. Нативный код
остаётся лучшим вариантом для многих разовых проходов и агрегатов. Собственный
общий query не заслужил публичного интерфейса: его прототип больше, имеет
ошибку вывода типов и непрояснённое удержание источника в Node. Сложные
инкрементальные отчёты решает TanStack DB; запросы к БД остаются у Drizzle.

Выбрана узкая комбинация гипотез «индексы над ссылками» и «прикладные операции
времени/диапазонов». Универсальная библиотека коллекций и собственная база
данных отклонены. Это выбор области полезности, а не уменьшение объёма проверки:
все семь обязательных бизнес-сценариев представлены в исследовании.

## Модель данных и контекстов

| Понятие | Ответственность |
|---|---|
| Ref | Ключ или исходный элемент; не обязательная обёртка |
| Entity | Сущность в хранилище, сохраняющая идентичность |
| Source | Iterable ссылок + resolver + контекст источника |
| Index | Снимок состава и структурных метаданных |
| Selection | Источник выбранных ссылок; сохраняет политику разрешения сущностей |
| Контекст источника | Зависимости resolver и геттеров построения |
| Контекст операции | Явные параметры конкретного фильтра, проекции или сортировки |

`from(map)` читает текущие ключи и текущие значения Map. Для Set/Array/Iterable
элемент одновременно является ссылкой и сущностью. Внешний getter можно задать
через `from(refs, { context, get })`. Он синхронный; получение данных по сети
выполняется до запроса. Для снимка сущностей явно используйте `new Map(store)`.

Индекс фиксирует состав, время/родителей/координаты при построении. Замена
сущности в живом хранилище видна при её последующем разрешении; новый ключ не
попадает в ранее построенный индекс. Изменение структурных метаданных требует
перестроения. Одна сущность может участвовать в нескольких индексах с разными
метаданными. Повторные появления в одном временном индексе требуют отдельных
occurrence IDs: уникальна ссылка записи, а не обязательно сама сущность.

При удалении сущности reference-only выборка может вернуть старый ключ.
Разрешение этого ключа через Map вызывает RangeError. Собственное значение
undefined отличается от отсутствующего ключа через has. У произвольного getter
обработка отсутствия определяется его контрактом. Одноразовый Iterable не
становится повторяемым после from; индекс потребляет его и сохраняет свои refs.

Source/привязанная Selection удерживает resolver и его контекст. Ленивая выборка
поддерева также удерживает топологию. Проекция возвращает обычные значения без
добавленного происхождения; если нужен ID, включите его в DTO самостоятельно.
Возвращённая сущность, getter или callback могут сами удерживать внешние данные.
Нельзя обещать освобождение всего источника только по типу результата.

Обобщения оправданы для Ref/Entity, контекста источника, контекста операции,
значения селектора и агрегата. Нет произвольной иерархии базовых коллекций,
глобального реестра адаптеров, async-движка или служебного объекта на каждый Ref.

## Выбор вместо общего query

Принимаем ограниченный `collect(source, options)`:

```ts
const rows = collect(from(storage), {
  context: { owner: selectedOwner },
  where: (event, id, ctx) => event.owner === ctx.owner,
  select: (event, id) => ({ id, title: event.title }),
  limit: 20,
});
```

Порядок фиксирован: where → select → limit. Без select результат содержит refs;
с select — значения проекции. Type guard сужает сущность для select. Resolver
вызывается один раз на посещённую ссылку, если нужны сущность/проекция; select
вызывается только после успешного where. limit=0 не читает источник, достижение
лимита закрывает итератор, исключение callback тоже закрывает его.

`sorted` сохраняет существующие Map/Set/Array/Iterable overloads и кеширование
значений перед устойчивой нативной сортировкой. Публичный Source-overload реализован
в [sorted.ts](../src/sorted.ts): третий аргумент
callback — контекст операции только при явных `{ context }` в четвёртом
аргументе. Контекст источника вместо него не подставляется. Пустой/одноэлементный
источник не вызывает селектор. Индексная сортировка сохраняет особый контракт
для допустимого undefined; прямая сортировка таких refs может отличаться.

Сортировка до лимита и после лимита — разные выражения:

```ts
const ordered = sorted(selection, item => item.title, compareTitle);
const page = collect(subset(selection, ordered), { where: isVisible, limit: 20 });
// Для «20 подходящих, затем упорядочить» сначала collect, затем sorted.
```

Нативные методы и прямые циклы остаются доступными. Дополнительные `filtered`,
`selected`, lazy take/drop и план query оставляем референсами; не создаём второй
набор синонимов для collect. Для расширенной ленивой/async-композиции используем
Ix, для обычных преобразований — нативный JS или Remeda. Pipe означает обычную
передачу результата между функциями, отдельный runtime не требуется.

Поиск/группировки/соединения проверены самостоятельными helpers, но не входят
автоматически в минимальное ядро. Found нужен там, где undefined — допустимый
результат поиска. Result/Optional не оборачивают каждый элемент. Решение об
экспорте отдельного helper требует повторяемого сценария, а не желания иметь
свой эквивалент каждой функции Remeda.

## Время

`timeline` из `ts-algo/time` — только временной индекс. Причинный граф
создаётся отдельно. Имена `startsBetween` и `overlapping` различают начало
события внутри окна и пересечение интервала. Оба возвращают привязанную выборку.
Публичный [пример расписания](../README.md#время-и-диапазоны) использует внешние
события, отдельные времена, контекст фильтра и независимые freeSlots/overloaded.
[Проверки](../test/time-operators.test.ts) подтверждают результаты.

```ts
const times = from(timeStorage);
const history = timeline(from(events), (_, id) => entity(times, id));
const selection = overlapping(history, { start, end });
const titles = collect(selection, { where: isConfirmed, select: event => event.title });
```

Контракт: `[start,end)`, нулевая длительность — точечное событие, пустое окно не
содержит событий; одинаковые начала сохраняют порядок источника. Некорректный
Date, нечисловое/бесконечное время, обратные границы и повторные refs отклоняются.
Date нормализуется при построении; изменение Date не меняет снимок.

Интерфейс ориентирован на date-fns Interval: start/end, Date или number. Строки
нужно разбирать заранее с явной политикой часового пояса. При смешении с Date
числа означают epoch milliseconds. Календарное addDays и длительность addHours
не равны на DST-переходе. Индекс не является календарём и не воспроизводит все
DateArg/context варианты date-fns; cross-realm Date лучше нормализовать в number.

Для редких запросов/частых правок предпочтителен проход. Для точек достаточно
отсортированных начал и бинарных границ. Max-end индекс полезен при повторных
выборочных пересечениях; много длинных/вложенных интервалов и большие результаты
могут сделать его невыгодным. [Стоимость и модель окупаемости](../experiments/goal/results/costs.md)
не являются универсальным порогом по размеру коллекции.

Исследовательский прототип материализует refs до collect. Публичные
startsBetween/overlapping возвращают ленивые повторяемые выборки: нормализуют
границы сразу, а поиск выполняют при итерации без промежуточного refs-массива.
collect с limit прекращает дальнейший поиск. Цена generator/Source заметна при
полной материализации, особенно малых результатов; все варианты, включая
проигрыши, сохранены в [миграционных измерениях](../experiments/goal/results/migration-time.md). Сам индекс реализует Source
в хронологическом порядке, поэтому его можно передать collect/sorted напрямую.

Политика date-fns: публичный TimeWindow определяется структурно как
readonly start/end: Date|number. Никакого импорта date-fns в JS или d.ts нет;
совместимость с установленным Interval<Date|number,Date|number> проверяется
compile-time. Это намеренно не весь DateArg: строки нормализуются вызывающим
кодом. Временной entry не добавляет peer/type-зависимость в core.

Диапазоны вынесены в ts-algo/ranges, каждая операция — отдельный модуль.
conflicts возвращает пары позиций входного массива; freeSlots считает union,
overloaded сравнивает суммарные units строго с capacity. Конечность входов и
нагрузки проверяется, точки не занимают длительность; точность IEEE-754
не превращается в точную арифметику.
[Публичные range-измерения](../experiments/goal/results/migration-ranges.md) включают
валидацию, сортировку и полную материализацию. В валидных fixtures новые
проверки формы/overflow не дали существенной регрессии относительно прототипа;
ошибочный-input контракт при этом строже. Dense conflicts требуют квадратичный
вывод пар, а direct native union остаётся полноценной альтернативой.

## Деревья, зависимости и пространство

Дерево хранит родительские связи отдельно от сущностей. `roots`, `children`,
`nextSibling`, `previousSibling`, `subtree` — самостоятельные функции.
Плоский sorted не меняет порядок детей; `sortChildren` возвращает новую
топологию с отсортированными группами соседей, сохраняя исходный порядок
в старой структуре и привязку сущностей. Контекст сортировки задаётся явно.
Геттер родителя может читать сущность или внешний источник. Несколько корней,
отсутствующие родители, циклы и замена сущностей проверены. Nullish refs нельзя
использовать как ключи дерева: они обозначают отсутствие родителя.

Результаты roots/children readonly на уровне TS и не заморожены.
Это контракт доверенного чтения, не runtime-защита от мутации JS-клиентом.
Публичные операции сохраняют этот контракт без скрытой копии на каждом чтении.
Tree реализует Source с preorder; subtree/ancestors ленивы и повторяемы.
Обход использует O(depth) состояния без копирования широких групп соседей.
sortChildren возвращает новый порядок групп, разделяет родительские связи и
сохраняет исходное дерево. Селектор одиночных групп не вызывается.

DAG helpers `dependencies`, `causesOf`, `effectsOf`, `descendants`, `ancestors`,
`causalOrder` — модуль ts-algo/dependencies. DAG реализует Source в порядке входа;
causalOrder возвращает привязанную выборку сохранённого Kahn-порядка.
Обходы в ширину ленивы, повторяемы, исключают начальный узел и дубли; прямые
связи — readonly-массивы. Связи/состав — снимок, сущности — живое чтение. Owner/status — поля сущности. Начальные независимые узлы идут по порядку входа, освобождённые — по очереди
Kahn; это не обещание лексикографически минимального порядка.
Общий редактируемый граф, сложные алгоритмы
и наблюдение событий делегируются Graphology. Дерево не заменяет DAG.

## Пространство

Статические точки: текущий pointIndex конкурентоспособен в проверенных
выборках, включая ближайшую точку; KDBush существенно компактнее в сохранённом
профиле. Flatbush/RBush подходят для другой модели геометрии, D3 — альтернативное
дерево. Их перестройку, размеры результата, порядок и tie/radius адаптацию
нельзя исключать из прикладной цены.

Область включительна; порядок refs в области не обещается. При равных расстояниях
выбирается первое вхождение источника, радиус включён. Ближайшая геометрическая
точка с последующим бизнес-фильтром отличается от поиска ближайшей разрешённой
точки: второй алгоритм не реализован и не заявляется.

Публичный ts-algo/spatial разделён на конструктор данных и независимые
within/nearest. Их импорты проверяются на установленном архиве двумя сборщиками:
поиск области не включает nearest, nearest не включает within. Старые методы
сохранены только как references. Индекс реализует Source в порядке входа;
within — ленивый повторяемый Source с фиксированными при вызове границами.
[Публичные spatial-сравнения](../experiments/goal/results/migration-spatial.md)
содержат полный путь поиска, entity filter/DTO, canonical order и отдельный build.
Цена Source resolver при построении выше прямого Map.forEach legacy в части
Node-входов, особенно совпадающих точек. Это превышает относительный порог и
принято за единый Source/context/live-entity контракт, не за ускорение алгоритма.
Ленивая область выигрывает при раннем limit; пустые/малые результаты платят
фиксированную цену Source/generator. Большие результаты с сортировкой могут
проиграть прямому проходу. Данные/поиски разделены физически, а не обёртками.

Расширение на динамические объекты/прямоугольники пока делегируем RBush/Flatbush,
не строим свой общий пространственный движок.

## Журнал отбора модулей

| Решение | Итог | Основание и цена |
|---|---|---|
| sorted + Source-overload | Сохранить/дополнить | Контракт кеширования/undefined и branded refs; нативная декорация конкурентна, Source имеет дополнительную цену разрешения |
| from/subset/entity + collect | Реализовать минимальным ядром | Меньше прототипа query, проверенные контексты/type guards/ранняя остановка; прямые циклы быстрее, allocation sampling дороже native |
| Общий query, lazy family | Оставить референсами | Ошибка literal take, лимит шагов, больше понятий и байт; для полной системы есть Remeda/Ix |
| Timeline + ranges | Разделить и реализовать | Предметная ценность, differential/DST/capacity проверки, маленький time-only импорт; статическая модель и стоимость результата |
| Tree | Упростить до топологии+функций | Внешняя иерархия и переходы; собственная скорость не превосходит разумный native индекс |
| Причинность | Отдельный optional DAG | Задачи/циклы/порядок, не включается в поиск времени; расширенный граф — Graphology |
| PointIndex | Сохранить узкий static scope | Прикладные area/nearest сравнения, меньший импорт; KDBush выигрывает представлением/памятью |
| Diff/indexBy | Небольшой отдельный модуль | Контракты ключей/undefined/дубликатов; прямые циклы столь же доступны, нет уникального алгоритма |
| Queue/deque/node lists | Сохранить алгоритмы в отдельных функциональных entries; legacy — references | Удобные end operations/handles; сравнения не дают общего выигрыша над native/Mnemonist |
| Map-backed list | Отклонить как default | Упрощённый Map draft проиграл узлам, ещё не имеет ownership checks |
| Priority processing | Native sort или optional Mnemonist | Heap выигрывает частичное извлечение, проигрывает полный batch; версии/отмена — явная политика приложения |
| QuickSort | Теоретические references | Не публичная замена native sort |
| Brand/density/Zod Mini | Сохранить узко | Проверка границы и сохранение типов; Brand не проверяет/не обеспечивает точность, Zod optional |
| Собственная БД, statechart, Decimal/Money | Исключить | TanStack/Drizzle, XState, decimal.js/Dinero решают эти области; новых преимуществ не доказано |

## Мутируемые последовательности и сверка

queue/deque/lists находятся в отдельных entries. Функции изменяют структуру
на месте, не копируют её ради функциональной формы. FIFO использует array/head,
deque — кольцевой массив с ростом; конструктор deque читает source один раз без
лишнего snapshot. Узлы списков имеют owner token; foreign/detached handles
отклоняются, clear отвязывает все узлы. Значения сохраняют идентичность.

Списки разделяют функции, но хранят только нужные ссылки: single — next,
double — next/previous. remove известного single-node ищет predecessor O(n),
double использует предыдущую ссылку O(1). insertBefore/removeLast — только double.
Операции находятся отдельно от конструктора, не вызывают старые методы.
Iterable даёт композицию с sorted и from/collect; Source с getter/context связывает
ID-значения с внешними сущностями. При итерации мутация не поддерживается.

indexBy/diffBy — отдельный модуль сверки по сценарию синхронизации. Первый
принимает значения Iterable и отклоняет duplicate key. Второй принимает две
ReadonlyMap с потенциально различающимися типами before/after и explicit equality.
added/changed сохраняют after order, removed — before order. Getter/equality
контекст передаётся явно в options; он не является source context. Ни общего
query, ни скрытой relational/reactive модели эти helpers не добавляют.

[Измерения последовательностей/сверки](../experiments/goal/results/migration-sequences.md)
сохраняют сравнения с legacy, native и Mnemonist. Разделение private insert/unlink
для single/double не устранило весь overhead: Node double-handle editing и часть
Bun single FIFO превышают относительный порог. Это принято за независимые
операции/проверку владения, с рекомендацией native batch/cursor или Mnemonist
для чистого throughput. Ни функциональная форма, ни собственный список не
объявляются универсально быстрее. Constructor-only импорты не включают
самостоятельные мутации, хотя построение узлов требует private insert.

## Профили кандидатов и доказательства

[Сравнительные таблицы](../experiments/goal/results/initial.md),
[бизнес/память/типы](../experiments/goal/results/business.md),
[доступ/сортировка/очереди](../experiments/goal/results/costs.md) — авторитетные
числа. Ниже профиль свойств, без произвольного общего балла.

| Кандидат | Корректность/DX/типы | Runtime/память/бандл | Поддержка |
|---|---|---|---|
| Native | Прозрачный контроль, ручное разрешение/контракты; простая типизация | Обычно дешевле; минимальный JS | Связующая логика повторяется в приложении |
| Remeda / Ix | Готовая композиция, больше возможностей | Зависит от Iterable/снимков; стоимость типов и bundle измерена | Экосистема поддерживает широкую поверхность |
| Fused query | Больше переходов типов/понятий; valid literal query отклоняется | Может уменьшать проходы, но не общий победитель; Node retention не объяснён | План, barriers и inference существенно сложнее |
| Restricted collect | Source + один options object; вывод/narrowing/DTO проверены | Меньше query, быстрее некоторых абстракций; native остаётся дешевле | Небольшой модуль с фиксированной семантикой |
| Time/Tree/DAG | Явные метаданные, ошибки построения; простые Ref generics | Цена построения/выборки/перестроения измерена; нет общего memory/type-cost ранга всех индексов | Разделяем предметные модули, не общий registry |
| TanStack DB | Другая модель — retained relational result | Холодный старт и больший бандл покупают incremental updates | Готовый сложный движок, не наш core |
| Spatial competitors | Разные geometry/order/radius contracts | Построение, запрос+DTO и footprint/retention измерены в пределах fixtures | Адаптер дешевле нового универсального индекса |

Типовая стоимость 5000 query call sites измерена отдельно от библиотечной
эмиссии; collect быстрее проверяется в этом fixture, но имеет больше
инстанцирований. Это не результат для IDE или каждого предметного индекса.
[Выведенные декларации](../experiments/goal/results/type-display.json) подтверждают
простые DTO[], branded ID[], Map ключей групп и Found. Ошибки планового query
не принимаются как публичный контракт. TanStack declarations требуют отдельного
skipLibCheck в проверенном strict-конфиге; факт и диагностики сохранены.

## Дополнительные задачи и границы

Ранние дополнительные кандидаты: ranges, сверка и indexBy. Дедупликация,
соединения и агрегация имеют проверенные helpers, но часто лучше обычный Map+
цикл или Remeda. Batch, sliding windows, rules, bounded history и журнал
изменений откладываем до явных требований к времени жизни/обновлениям.

Не планируем собственный FixedPoint следующим модулем. Сначала выбираются
представление числа, безопасный диапазон и округление. Точные суммы нельзя
получить брендом над number; существующие decimal.js/Dinero должны быть
исходным выбором. Source может сохранять такие сущности/значения без владения
их арифметикой. IEEE-754 диапазоны/координаты/capacity не становятся точными.

Сложные переходы, эффекты и persistence — XState; инкрементальные отношения —
TanStack; удалённые данные и SQL — слой БД. LINQ служит ориентиром интерфейса,
а не прямым runtime-конкурентом. Браузерные throughput/peak/latency и динамические
пространственные индексы не доказаны измерениями Node/Bun на одном M5.

## Карта миграции публичного API

База сравнения — `bd9a160`, завершённое исследование. Пакет private, переход
может содержать несовместимые изменения; временные совместимые обёртки не
считаются завершением миграции. Сначала переносится ядро, затем предметные
структуры, сценарии и поставка. Все исторические структуры с методами исключены
из публичной реализации и остаются в references. Старый timeline исключён
из src/публичных exports и сохранён только в references для сравнений. Build
очищает dist, чтобы перемещённые JS/d.ts не попадали в архив как stale-файлы.

| Область | Перенос и переработка | Целевой импорт | Статус |
|---|---|---|---|
| Ядро | Source/from/subset/entity, фиксированный collect, Source-overload sorted; прямые Map/Array пути сохранить | ts-algo | Реализовано, публичные runtime/type тесты проходят |
| Время | Вместо ReadonlyMap с методами — временной индекс и независимые startsBetween/overlapping | ts-algo/time | Реализовано; legacy перенесён в references |
| Диапазоны | freeSlots/conflicts/overloaded с полуоткрытыми интервалами | ts-algo/ranges | Реализовано, независимые оракулы |
| Дерево | Внешняя топология, живые сущности; roots/children/соседи/subtree/sortChildren | ts-algo/tree | Реализовано; legacy вынесен из поставки |
| Причинность | Удалить из timeline, отдельный DAG и симметричные обходы | ts-algo/dependencies | Реализовано отдельно от времени |
| Пространство | Данные статического индекса отдельно от within/nearest, сохранить точность/ties/radius | ts-algo/spatial | Реализовано: данные + независимые операции |
| Последовательности | Сохранить алгоритмы, вынести из core, заменить пользовательские методы независимыми операциями | ts-algo/queue, /deque, /lists | Реализованы функции над данными |
| Сверка | indexBy/diffBy по сценариям, не общий relational engine | ts-algo/diff | Реализованы indexBy/diffBy |
| Контракты | Brand/isDenseArray в core; Zod Mini отдельно | ts-algo/zod | Реализовано; установленный consumer проверяет Zod Mini |
| Теоретические алгоритмы | QuickSort и отвергнутый query вне публичных exports | references / experiments | Сохраняются вне поставки |

Несовместимые изменения: предметные импорты уходят из корня; методы заменяются
операциями; дерево перестаёт снимком хранить сущности; timeline больше не
предоставляет причинный граф и собственную бизнес-фильтрацию. README и примеры
меняются одновременно с соответствующим модулем, затем проверяются как
потребители установленного архива. Имя операции без такой реализации не
доказывает гранулярности бандла.

`from(source)` сохраняет уже созданную привязку, включая resolver/context.
Для явной перепривязки используйте `from(source, {get,context})`. subset не
копирует переданный Iterable; снимок создаётся явным массивом. Массивы в from
следуют стандартной итерации JS, в том числе превращают дырки в undefined;
контракт плотности прямого sorted(Array) не меняется.

Проверка публичных дерева/DAG сохранена в
[миграционных сравнениях](../experiments/goal/results/migration-structure.md).
Нативные индексы остаются базой сравнения; полный cold путь включает проверку
связей. Кешированный порядок экономит повторный Kahn-обход, но хранит ещё один
массив refs. Внутренняя привязка плотного массива даёт reference-only collect
нативный slice, только пока её итератор не заменён. Arbitrary from/subset не
используют этот путь, чтобы сохранить семантику дырок и пользовательских
итераторов. Промежуточный вариант Array.from отвергнут по замерам, а не скрыт.
В готовых task-query есть цена живого resolver/collect против прямого
фильтра materialized Map entries в прототипе. Рост выше относительного порога
принят за выбранный контракт привязки, с явной рекомендацией direct indexed
loops там, где важнее минимальная цена одного прохода. Нет обещания fastest query.

### Критерии проверки до измерений

- Корректность, callback-order/count, сохранение ссылок и type safety: регрессии
  не допускаются. Замена публичного контракта должна быть явной в этой карте.
- Runtime: для эквивалентных сохранённых горячих путей рост медианы более 15%
  при превышении разброса — повод разбирать и повторно проверять причину;
  для операций дешевле 0.01 ms дополнительно учитывать абсолютную цену. Это
  порог расследования, не автоматическое принятие меньшей регрессии.
- Новые операции сравниваются с прототипом и разумным native baseline.
  Прямой цикл вправе выиграть; дополнительный runtime должен покупать заявленную
  композицию/контракты. Подменять Map путь Source resolver запрещено.
- Бандл: core не включает предметные модули/Zod/date-fns; импорт одной операции
  исключает остальные обещанные алгоритмы. Рост эквивалентного consumer более
  10% требует объяснения включённых модулей. Fixture-код учитывать отдельно.
- Типизация: strict/noUnchecked/exactOptional, положительные/отрицательные
  public-consumer примеры; для затронутых типов повторить scaled checking.
  Рост времени/памяти более 20% требует рассмотрения при сопоставимых прогонах.
- Память: bound Source удерживает зависимости намеренно; не добавлять служебный
  объект на элемент и не обещать освобождение по виду результата. Сравнивать
  retention и natural allocation отдельно, profiler-ограничения сохранять.

Промежуточная проверка ядра сохранена в
[сравнении публичного core](../experiments/goal/results/migration-core.md).
Source-dispatch увеличивает bare sorted import, а полное распознавание Map и
сохранение существующих bindings увеличивают from/collect против упрощённого
array-прототипа. Рост выше bundle-порога разобран: это фиксированная цена
выбранных контрактов, без подтягивания предметных модулей и Zod. Она принимается
для ядра; увеличение каждого следующего entry требует отдельного объяснения.

Финальная приёмка требует семи сценариев на публичных импортах, двух сборщиков,
Node/Bun, строгого consumer установленного архива и документации фактического
API. Проверка только ядра не завершает миграционный Goal.

## Неопределённости и их влияние

Наблюдаемое удержание projected query в Node и unbound temporal getter в Bun
не объяснено retainer graph. Поэтому query не продвигается, а unbound индекс
не рекламируется как гарантия освобождения хранилища. Restricted numeric
projection освобождает Map в проверенных cases, не в любом пользовательском
callback. Bound Source намеренно удерживает зависимости.

Allocation sampling — оценка с влиянием Inspector; Bun не имеет того же профиля
в эксперименте. Heap после GC не равен полной цене выделений, observed heap
maximum не равен peak. Публичная cached sorting и нативная декорация теперь имеют отдельное
sampled-allocation сравнение, но оно не измеряет точные полные выделения. Малые/перекрывающиеся времена не дают общего победителя.

Семь фиксированных fixtures и 60 seeded rounds каждого сценария проверяют
сочетания относительно независимых оракулов, но не заменяют production trace. Преимущество DX здесь — меньше повторяемой связующей логики и ясные типы,
а не результат пользовательского исследования. Отсутствие этих гарантий
ограничивает обещания, не требует создавать универсальную библиотеку.

### Публичные примеры, типизация и память

Семь [публичных примеров](../examples/business.ts) используют bare imports,
независимые функции и нативные операции для группировки/приоритетной политики.
Одинаковый фиксированный expected-result fixture проверяется root-тестом и
после установки архива в отдельный consumer. Дополнительно
[60 seeded rounds каждого сценария](../test/business-oracles.test.ts) сравнивают
публичные цепочки с path membership, scans, all-pairs и elementary time cells;
этот тест также выполняется внутри установленного consumer. Выведенные return types сохраняются
в [отчёте inference](../experiments/goal/results/migration-business-types.json).

[Scaled type checking](../experiments/goal/results/migration-types.md) сравнивает
готовые декларации core с прототипом, native и Remeda на 100/1000/5000 независимых
вызовах, без аннотации результатов. Это отдельная проверка от installed exports.

[Публичная память](../experiments/goal/results/migration-memory.md) подтверждает
намеренное удержание bound источников и отсутствие Map у numeric projection в
проверенном fixture. Unbound timeline и queue показывают различие удержания Map
между Node и Bun; без retainer graph не выводим механизм и не обещаем освобождения.
Queue/списки сохраняют сами сущности независимо от состояния исходного Map.
Allocation sampling Node для cached/decorated sort и collect дополняет retained
snapshots; эти данные не дают эквивалентного allocation-профиля Bun или peak.

Проверка scaled types выявила стоимость, которой не было видно по обычным
fixtures: тысячи отдельных inline-вызовов sorted компилируются существенно
дольше нативной декорации; collect также превышал порог против прототипа.
Перестановка overloads не помогла и отклонена. Изолированные упрощённая
сигнатура, NoInfer и переиспользование callbacks проверены в
[диагностическом эксперименте](../experiments/goal/results/migration-type-investigation.json).
Они не оправдывают потерю Map/Source контрактов. Дополнительное
[сравнение с исходной версией и раскладкой модулей](../experiments/goal/results/migration-type-baseline.json)
показывает: большой одиночный модуль медленный уже до миграции; public sorted
в нём дополнительно дороже. Этот рост принимается за Source/context overloads
и защиту от неправильного native fallback. При 5000 вызовах в 50 модулях цена
array sorted около 0.39 s против 0.37 s before, collect около 0.54 s против
0.50 s prototype; Map/Source проверены отдельно. Это не обещание IDE latency
или инструкция делить код. Ограничение большого модуля сохраняется явно,
а меньшие результаты не подменяют исходный неблагоприятный fixture.

Отдельно исправлена type-safety ошибка: native fallback-overloads sorted
исключают Source binding даже у пересечений Array/Map/Set. Структурный
Map/array hybrid выбирает Map-семантику. Эти правила проверяются положительными
и отрицательными compile-time случаями, а Source/native priority — runtime-тестом.
