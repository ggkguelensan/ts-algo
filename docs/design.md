# ts-algo: повторяющиеся задачи бизнес-логики

Библиотека помогает находить свободное время, выбирать объекты в области,
упорядочивать ссылки и считать суммы без потери точности. Простой интерфейс,
опора на встроенные средства JS и измеряемая стоимость важнее числа алгоритмов.

TypeScript добавляет статические типы к JavaScript, но не собственный runtime
коллекций. Поэтому здесь две разные задачи: выразить ограничения типами без
runtime-кода и дать операции, которых нет у стандартных коллекций.

## Что уже есть

- `sorted`: кеш значений и устойчивая нативная сортировка индексов.
- `isDenseArray` и опциональный `denseArray` из ts-algo/zod: проверка
  исходных массивов без дырок. [Контракт](validation.md).
- `pointIndex`: статический индекс 2D-точек, поиск в области и ближайшей точки.
- `tree`: лес из Map, обходы, переходы next/previous среди соседей и их устойчивая сортировка.
- `timeline`: точки/интервалы, внешние источники через context/get и причинный DAG. [Контракты](tree-timeline.md).
- `queue`/`deque`: FIFO и оба конца в массивах; `linkedList`/`doublyLinkedList`: стабильные узлы. [Контракты](sequences.md).

Учебный Quicksort вынесен в [references](../references/README.md); он используется
только тестами и бенчмарками, не экспортируется библиотекой.

Модули, отмеченные как будущие, — проектирование, не существующие функции.
Пакет пока private; публикация и стабильный контракт версии ещё впереди.

## Приоритеты

| Очередь | Задача бизнеса | Полезный модуль / тип | Основа реализации |
|---|---|---|---|
| Есть | Порядок строк, карточек, сущностей | Сортировка ссылок | Array.sort + кеш |
| Есть, первый вариант | Выделение точек в редакторе, ближайший маркер | PointIndex | Квадродерево + массивы ссылок/координат |
| Есть | Каталоги, владельцы, структура задач | Tree / forest | Map + списки детей, нативная сортировка соседей |
| Есть | История действий, аудит, связанные события | Timeline + causal DAG | Отсортированные начала, max-end для интервалов, граф связей |
| Есть | FIFO, оба конца, локальные правки по узлам | Queue / deque / linked lists | Массивы или стабильные узлы по задаче |
| Следующая | Записи, бронирования, занятые периоды, свободные слоты | Операции над интервалами | Нативная сортировка + проход; индекс только для повторных запросов |
| Следующая | Суммы, проценты, скидки, распределение оплаты | FixedPoint / денежные операции | BigInt, явные scale и rounding |
| Затем | Пересечение карточек и прямоугольников | Индекс прямоугольников | Сравнить линейный обход, пространственную сетку и R-tree |
| Затем | Частый поиск в отсортированных данных | lowerBound / upperBound | Бинарный поиск в Array / TypedArray |
| По реальному сценарию | Очередь заданий, ближайший дедлайн | PriorityQueue | Двоичная куча в массиве |
| По реальному сценарию | Ограниченная история, поток последних событий | RingBuffer | Буфер фиксированной ёмкости |
| По реальному сценарию | Зависимости шагов, циклы в правилах | Операции над графом | Map / Set + топологический порядок |
| По реальному сценарию | Точные отношения, пропорции, преобразования | Rational | Пара BigInt + сокращение дробей |

Собственные Map/Set и отдельная коллекция на каждый алгоритм пока не нужны.
Очереди и связные списки добавлены для разных операций: хранение без узлов и локальные правки по handles. Критерий добавления: повторяющаяся задача,
которую иначе приходится сложно и небезопасно решать во многих приложениях.

## Интерфейс и ссылки

Источники — существующие протоколы: `ReadonlyMap<Key, Entity>` и `Iterable<Ref>`.
Map передаёт селектору сущность и ключ, возвращаем ссылку-ключ. Set, массив и
Iterable возвращают сам элемент. Селектор внешнего хранилища остаётся возможен.
Индексы не владеют сущностями и не изменяют их; получение координат/ключей
спрятано внутри. Новую структуру сначала подключаем через существующий протокол.
Специальный адаптер добавляем, когда нужна действительно другая семантика.

Целевой интерфейс — структуры с данными и отдельно импортируемые функции.
Пользовательские методы коллекций заменяем операторами; архитектура перехода
описана ниже. Нативные Array/Map/Set сохраняют свои методы и поведение.
Настройка алгоритма, fluent-цепочки, глобальные реестры и обязательные обёртки
каждой сущности усложняют интерфейс и увеличивают runtime. Их стоимость должна
оправдываться конкретной задачей. Выбор алгоритма обычно остаётся внутри модуля.

```ts
const places = new Map([
  ["office", { x: 100, y: 40 }],
  ["warehouse", { x: 900, y: 300 }],
]);
const index = pointIndex(places, { x: place => place.x, y: place => place.y });
const visibleKeys = index.within({ minX: 0, minY: 0, maxX: 200, maxY: 100 });
// ["office"], string[]
const closest = index.nearest(105, 40, 20);
// { reference: "office", distance: 5 } | undefined
```

## Функциональная архитектура: решение и план перехода

Правило принято: собственные коллекции не предоставляют бизнес-операции
методами. Ни `.filter`, ни `.sortBy`, ни `.overlapping`, ни `.enqueue` на них
не оставляем. Стандартный протокол `[Symbol.iterator]` сохраняем для работы
с `for...of`, spread и нативными средствами. Свойства `size`, `context` и
ссылки на позиции допустимы; они не являются цепочкой операций.

Это целевая архитектура. Текущий код и примеры выше ещё используют методы;
перечисленные ниже query/filtered/pipe и самостоятельные операции пока не
реализованы. Миграция должна одновременно менять реализацию, типы, тесты,
примеры и бенчмарки, а не добавлять постоянный второй интерфейс.

### Данные, индексы и операции

1. Нативные источники хранят сущности. Общие алгоритмы принимают Array,
   ReadonlySet и Iterable как элементы, ReadonlyMap как ключи и сущности.
2. Наши структуры хранят порядок ссылок, топологию или индекс. Они дают
   непрозрачный handle и стандартную итерацию, но не комплект алгоритмов.
3. Отдельные функции читают или меняют внутреннее состояние через внутренний
   интерфейс модуля. Вызывающий код не получает доступ к изменяемым массивам
   индекса, чтобы не нарушать его инварианты.
4. Query сохраняет связь между Ref, Entity и Context до материализации
   результата. Точка подключения источников — внутренний адаптер; встроенные
   адаптеры нужны для Iterable, Map и наших индексированных структур.

В частности, Tree/Timeline перестают изображать ReadonlyMap собственными
методами get/has/entries. Нативный Map остаётся источником. Для внешнего
хранилища сохраняем явно переданный resolver и context. Итерация наших
ссылочных структур выдаёт ссылки; адаптер сообщает query, как получить
сущность. Без адаптера обычный Iterable считается коллекцией самих элементов.

Внутреннее состояние можно хранить в поле с закрытым Symbol; единый глобальный
реестр и обязательный WeakMap для всех структур не нужны. Окончательное
представление выбираем по размерам и замерам. Структуры изменяемы там, где
этого требует задача очереди/списка; функциональная форма вызова не обещает
копирование структуры при каждом изменении. Сущности алгоритмы не изменяют.

### Имена и форма вызова

Используем `query`, `filtered`, `sorted`, `take`, `pipe`. Не вводим синонимы
queried/filted/sortedReferences. Query выполняет запрос, sorted/filtered
возвращают выбранные ссылки; pipe передаёт значение обычным функциям.

Предлагаемые перегрузки сохраняют быстрый прямой вызов:

```ts
const activeIds = filtered(users, user => user.active);
const rankedIds = sorted(users, user => user.rank, compareNumbers);

const ids = query(
  users,
  filtered(user => user.active),
  sorted(user => user.rank, compareNumbers),
  take(20),
);
```

Это иллюстрация формы, а не готовый исполняемый пример. Для Map результат —
массив ключей, но следующий предикат/селектор получает сущность, ключ и
контекст. Для Array/Set результат содержит исходные элементы. Вывод типов
должен сохранять бренды ссылок и сужение сущности после type guard.

Специфические операции доступны только подходящим структурам:

| Область | Предлагаемые самостоятельные функции |
|---|---|
| Tree | parent, children, nextSibling, previousSibling, subtree, sortedSiblings |
| Timeline | between, overlapping, timeOf |
| Причинный граф | causesOf, effectsOf, ancestors, descendants, causalOrder |
| PointIndex | within, nearest |
| Queue | enqueue, dequeue, peek, clear |
| Deque | pushFront, pushBack, popFront, popBack, clear |
| Связные списки | append, prepend, insertAfter, insertBefore, remove, clear |

Имена с одинаковым смыслом можно перегружать по структуре. Не объединяем
разные операции только ради общего имени. Например, sorted(tree, ...) —
плоский массив ссылок, sortedSiblings(tree, ...) — новое дерево с изменённым
порядком соседей. Мутации получают коллекцию первым аргументом и не становятся
шагами query. Скалярный nearest тоже не обязан быть шагом выборки.

### Исполнение query

Query синхронно исполняет шаги слева направо и возвращает новый массив ссылок.
Не создаёт скрытый долгоживущий кеш и не превращает одноразовый Iterable в
повторно используемый источник. Промежуточное состояние сохраняет источник
и resolver, а не только массив уже отобранных ключей.

Предикаты и селекторы чистые; во время запроса источник и внешние данные
не изменяются. Это позволяет объединять соседние фильтры в один проход с
коротким замыканием, без отдельного массива на каждый шаг. Сортировка — этап,
который требует собрать всю входящую выборку; значения селектора кешируются.
Служебные массивы сортировки сохраняются там, где нужны реализации.

take перед sorted ограничивает сортируемую выборку; take после sorted требует
сортировки всей выборки. Шаги не переставляем. Индексный шаг использует индекс
для поиска кандидатов, сохраняя семантику позиции шага и порядок фильтрации.
Произвольные шаги не обещают один проход; стратегии top-k пока не добавляем.

Коллекции с индексами не должны молча попадать в обычный линейный обход.
Типы ограничивают overlapping Timeline, subtree Tree и within PointIndex.
Общий исполнитель не импортирует все предметные алгоритмы: описание шага
приносит нужную реализацию из отдельно импортируемого модуля. Объекты шагов
или замыкания допустимы на запрос, но не обязательны на каждый элемент.

### Размер модулей и зависимости

Замена `history.overlapping(...)` на функцию, вызывающую старый метод,
не решает задачу удаления неиспользуемого JS. Конструктор создаёт данные
индекса; отдельно импортируемые операции используют их напрямую. Код
обхода причинного графа не должен импортироваться временной выборкой.

Причинный индекс планируем строить отдельно и явно связывать с той же
коллекцией ссылок. Это позволяет хранить время без DAG, а связи использовать
для событий или других сущностей. Временные и пространственные индексы также
не требуют друг друга. Существующие гарантии снимка метаданных и внешнего
получения сущностей должны остаться явно описанными.

Корневой ESM entry служит удобному импорту, предметные entry points —
изолированному импорту. Их package exports ещё предстоит оформить. Ни один
модуль реализации не импортирует корневой barrel. Tree-shaking подтверждаем
на исполняемом готовом бандле, а не только устройством исходных файлов.

### Независимые функциональные примитивы

- Brand уже реализован как тип без runtime-зависимости. Проверку внешних
  значений рекомендуем поручать Zod Mini на входе приложения; алгоритмы
  сохраняют как собственные бренды, так и бренды Zod.
- Pipe — небольшой синхронный исполнитель обычных функций. Он не раскрывает
  Result/Optional и не ловит ошибки автоматически.
- Result планируем для ожидаемых бизнес-ошибок с формой success/data/error,
  структурно совместимой с safeParse Zod, и отдельными map/flatMap/mapError.
- Optional нужен, если undefined является допустимым найденным значением;
  в остальных случаях достаточно T | undefined. Пустая выборка query — [].

Эти примитивы не являются обязательными контейнерами для каждой операции.
Тип Result стирается, но создание объекта результата имеет runtime-стоимость.

### Проверка и последовательность миграции

Сначала выделяем доступ к данным и переводим Tree/Timeline/PointIndex на
самостоятельные операции с сохранением контрактов. Затем добавляем прямой
filtered, перегрузки шагов sorted/filtered и query/take. После этого переносим
мутации очередей и списков в функции и добавляем pipe. Result/Optional — по
конкретным бизнес-сценариям, без большого обязательного FP-runtime.

Для каждого этапа проверяем вывод типов, идентичность сущностей, порядок,
обработку пустых источников, branded keys и внешнее получение данных. Измеряем
прямую операцию и query против эквивалентного ручного кода на Node/V8 и
Bun/JavaScriptCore: небольшие и большие источники, один и несколько фильтров,
выборочный индексный запрос, построение плюс запросы, отдельные импорты и
корневой entry. Объём памяти и выделения измеряем отдельно: меньший gzip не
доказывает меньшую память. Сохранять имена старых методов после миграции не
планируем.

## Пространство

Текущий `pointIndex` строит bucket-quadtree: каждая область делится пополам по
двум осям, образуя до четырёх дочерних областей. Корневая область — ограничивающий
прямоугольник точек, поэтому ячейки могут быть прямоугольниками. В листе обычно
до 16 точек; глубина ограничена 32. Листы могут содержать больше точек, когда
разделение остановлено из-за глубины или точности чисел. Это ограничивает
рекурсию на вырожденных входах и сохраняет все совпадающие точки.

Координаты кешируются один раз на каждое вхождение. Делится один массив индексов;
массивы точек в дочерние узлы не копируются. Runtime хранит ссылки, x, y, порядок,
объекты узлов и массивы их дочерних узлов. TypedArray пока не используется:
возможная экономия памяти требует отдельного измерения, включая построение.

- `within` включает все четыре границы, порядок результата не определён.
- `nearest` использует евклидово расстояние; радиус включён, по умолчанию Infinity.
  При равном вычисленном расстоянии выбирается первое вхождение в источнике.
- Отсутствие результата — `undefined`; найденная ссылка находится в объекте,
  поэтому ключ `undefined` не путается с отсутствующим результатом.
- Пустой индекс допустим. Для индекса даже единственная точка требует координат.
- Координаты и границы запросов конечны; неверные значения/границы/радиус вызывают
  RangeError. Вычитание очень больших конечных координат всё ещё может дать
  Infinity; вычисления остаются арифметикой JS number, не точной геометрией.
- Индекс — снимок координат и состава, но ссылки на сущности остаются исходными.
  После изменения позиций или состава строим новый индекс. Селекторы не должны
  изменять источник; Iterable должен быть конечным, массив — плотным.
- При максимальной глубине D построение ограничено O(nD), рекурсия O(D).
  Запросы в худшем случае обходят все узлы и точки: ускорение зависит от данных,
  размера области и возможности отбрасывать ветви. Запрос всей области требует
  как минимум O(k) для k возвращаемых ссылок. Обещания O(log n) для любого запроса нет.

Для прямоугольников один индекс центров недостаточен: большой объект может
пересекать область, хотя его центр снаружи. География тоже отдельный контракт:
долгота/широта, переход через 180°, проекция и расстояние на поверхности.
`pointIndex` работает в плоскости с единицами координат вызывающего кода.
В качестве внешнего ориентира для последующих сравнений есть
[d3-quadtree](https://d3js.org/d3-quadtree); сейчас benchmark сравнивает с нативным
линейным поиском, а не с d3 и не доказывает превосходство над другими индексами.

## Время: хронология и будущие операции интервалов

Первый контракт: полуоткрытые интервалы `[start, end)`. Запись 10:00–11:00 и
11:00–12:00 не конфликтуют. Объединение соприкасающихся интервалов для покрытия
должно быть явно согласовано отдельно от определения конфликта.

Сначала нужны объединение занятых интервалов, пересечение, вычитание и свободные
слоты внутри окна. Для отображения — выбор событий в окне с возвратом исходных
ссылок. Для количества одновременно занятых ресурсов — проход по границам.
Это полезнее, чем сразу выставить наружу универсальное IntervalTree.

Для редкого расчёта достаточно сортировки и линейного прохода. Для повторных
запросов хронология уже использует массив начал и max-end индекс при наличии
длительностей. Один бинарный поиск
по start не решает задачу, если длинные ранние интервалы пересекают позднее окно.
Сравниваем также полную стоимость построения/обновления и запросов.

Разделяем момент времени, длительность и календарную дату. Бренды единиц
milliseconds/seconds и Instant/Duration можно стереть из JS. Конструктор на
внешней границе проверяет конечность/диапазон; операции внутри опираются на
контракт. Календарные дни и месяцы не сводим к фиксированному количеству ms.

Выбранный интерфейс для дат и календарных операций — [date-fns](https://date-fns.org/).
Это архитектурное решение библиотеки, а не утверждение об универсальном
стандарте всех приложений. Temporal не является основой временного модуля.
Не создаём собственную систему календарных дат или копии функций date-fns.

Планируем опираться на его DateArg, Interval и Duration, импортируя типы через
import type. Для нормализованных входов Timeline используем Date или timestamp
в миллисекундах, то есть подмножество DateArg без строк. Строки разбираются
явно через parseISO или parse с заданным форматом на входе приложения.
Date-подклассы должны проходить без приведения к новому базовому Date.
Календарные длительности Duration не подменяем числом миллисекунд.

Иллюстрация будущих типов; сейчас публичный Timeline ещё принимает числа:

```ts
import type { DateArg, Interval } from "date-fns";

type TimelineDate = Exclude<DateArg<Date>, string>;
type TimelineInterval = Readonly<Interval<TimelineDate, TimelineDate>>;
```

Date/Interval преобразуем в числовые значения один раз при построении индекса,
границы запроса — один раз на запрос. Поиск и сортировка кешированных времён
работают с числами, без создания Date в компараторах и при обходе дерева.
Date изменяем, поэтому индекс хранит снимок времени, а не полагается на
неизменность Date-объекта. Исходные сущности и даты не изменяем.

Формат Interval { start, end } совместим с date-fns, но семантику границ
задаёт операция. В частности, [isWithinInterval](https://date-fns.org/docs/isWithinInterval)
включает start и end; наша хронология сохраняет полуоткрытый контракт [start, end).
Перевёрнутые границы отклоняем, а не молча переставляем. Invalid Date и
неконечные timestamp отклоняем на входе; корректность календарных границ
проверяем до построения индекса.

Календарные расчёты и разбор/форматирование поручаем отдельно импортируемым
функциям date-fns. Для явно заданных часовых поясов используем его экосистему
[@date-fns/tz](https://github.com/date-fns/tz) и контекст календарной операции.
Контекст источника сущностей Timeline и контекст часового пояса имеют разные
назначения; не перегружаем один параметр двумя смыслами.

При реализации нового временного интерфейса date-fns подключаем через
предметный entry и peer dependency. Алгоритмы очередей, сортировки и
пространственного поиска не импортируют его runtime. Если публичные
декларации используют типы date-fns, потребителю временного модуля требуется
пакет даже при отсутствии runtime-импорта; это отражаем в зависимости и
документации. Полифилл Temporal в основной импорт не добавляем.

Сейчас date-fns не добавлен в зависимости: проверен пример использования
с date-fns 4.4.0 через числовой селектор текущего Timeline. Переход публичных
типов и прямой приём Date выполняем вместе с миграцией временных операций
на самостоятельные функции, а не через постоянный второй интерфейс.

## Точные вычисления — следующий модуль

Начинаем с фиксированной точности на BigInt: например, сумма в минимальных
единицах валюты. Суммы, валюта, scale и режим округления — часть контракта.
BigInt поддерживает точные целые, но не обеспечивает десятичные дроби сам по себе.
BigInt не обязательно быстрее number; сравниваем стоимость, сохраняя одинаковые
требования к точности. Погрешность number не является корректным baseline.

Бизнес-операции: парсинг десятичной строки, точное сложение, применение ставки с
явным округлением, распределение суммы по весам с сохранением общей суммы.
Например, 100 минимальных единиц на троих должно дать 34 + 33 + 33 по согласованному
правилу остатка. Остатки и равные веса должны иметь детерминированный порядок.

Вход для точных дробных значений — строка, а не уже округлённый number.
Для операций между BigInt и number нужны явные преобразования и ограничения.
Деление, отрицательные значения, округление половин, scale, сериализация в JSON
и смешение валют должны быть определены до реализации. Intl используется для
представления, а не для вычисления. У валют нельзя молча предполагать две цифры.

Сначала фиксированная точность; Rational и произвольная Decimal — по подтверждённым
сценариям. [Decimal](https://tc39.es/proposal-decimal/) рассматриваем как отдельное
предложение платформы, не как доступную сегодня зависимость: в двух локально
проверенных runtime глобального Decimal нет.

## Большой TypeScript, маленький JavaScript

Можно добавлять overloads, conditional types, readonly, declaration-файлы и
бренды через `declare const ...: unique symbol`: они не требуют runtime-кода.
Это помогает различать деньги и количество, секунды и миллисекунды, координаты
разных пространств. Не создаём runtime Symbol на каждый такой тип.

Однако типы не проверяют внешние JSON-данные. Проверки на входе и правила
арифметики остаются необходимым JS. Нужен компромисс: проверить данные при
создании значения/индекса, затем не повторять проверки в каждом внутреннем шаге.

Runtime-стоимость оцениваем отдельно: байты JS и gzip, время построения, запроса
и обновления, выделения объектов и память. `!` и `as` в доказанных индексных
операциях стираются; дополнительные объекты и массивы — нет. Нативные методы
не автоматически быстрее циклов: выбор подтверждаем замерами.

ESM-экспорты позволяют удалять неиспользуемые функции. Нет глобальной инициализации
индексов или обязательного полифилла. Основные алгоритмы не имеют
runtime-зависимостей; отдельный entry ts-algo/zod требует опциональный Zod.
В текущем Bun 1.3.14
эксперимент с `sideEffects: false` выдавал сломанные barrel-бандлы без определений
экспортируемых функций, поэтому поле не добавлено. Benchmark бандла импортирует
готовый JS и проверяет его экспортируемые функции до записи размеров. Это
наблюдение конкретной версии/проекта, не общий запрет на эту настройку.

## Проверка производительности

Один и тот же скомпилированный JS запускаем в Node/V8 и Bun/JavaScriptCore:
[документация Bun](https://bun.sh/docs/runtime). Записываем версии, CPU,
распределение входа, размеры, число запросов, прогрев и число образцов.

Нативный baseline должен выполнять ту же работу: возвращать ссылки, сохранять
источник и соблюдать тот же числовой/временной контракт. Замеры только готового
индекса не показывают цену решения. Отдельно считаем построение и построение
вместе с запросами. Для динамических структур потребуется цена обновлений.

Нужны равномерные и кластерные данные, повторы, границы, большие результаты,
малые коллекции и редкие запросы. Правильность проверяем отдельно от времени
против простого решения; варианты чередуем. Медиана вместе с min/max сохраняется
в JSON. Малые различия считаем поводом повторить запуск, не победой алгоритма.

Node и Bun помогают исследовать два движка, но не заменяют Chrome/Safari на
устройствах пользователя. Нынешний spatial benchmark не измеряет peak heap и
браузеры; это следующие проверки перед обещаниями о памяти и frontend-нагрузке.
Для каждого модуля также измеряем импорт через общий ESM entry с удалением
неиспользуемых экспортов: сырой minified JS и gzip. Жёсткий размерный бюджет пока
не задан; показываем фактическую цену каждой возможности.

## Порядок следующей работы

1. Выполнить переход к самостоятельным операциям и query по архитектуре выше.
2. Обсудить контракты интервалов и money/fixed-point на конкретных задачах.
3. Реализовать операции интервалов без сложного индекса; сравнить с простым
   нативным решением в обоих runtime и измерить бандл.
4. Реализовать fixed-point и распределение сумм; проверить правила точности
   и округления на независимых примерах.
5. По реальным данным выбрать индекс прямоугольников и способ обновления.
6. Добавлять приоритетную очередь, динамические индексы и отдельные операции графов по конкретным сценариям.

Сложность внутреннего алгоритма допустима, если вызывающий код получает простой
контракт, а измерения показывают, за что он платит временем, памятью и байтами.
