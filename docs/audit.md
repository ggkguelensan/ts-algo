# Аудит ts-algo

Это исторический аудит исходной реализации, не текущий журнал решений.
Упаковка исправлена, сравнения и прототипы сохранены в
[исследовании](../experiments/goal/research.md). Актуальная цель и выбор модулей —
[design.md](design.md); рекомендации ниже относятся к состоянию аудируемого
commit и не требуют повторного внедрения уже выполненных исправлений.


Дата: 2026-10-05. Проверяемая реализация: `5933038`.
Область: src, публичные exports, документация, тесты и методика бенчмарков.
Это отчёт с находками и экспериментами, не внедрение предложенных изменений.

Проверки: npm run check; 45 runtime-тестов на Node и Bun; реальный npm tarball
в отдельном consumer package scope; npm ci с отслеживаемым lockfile;
примеры владения сущностями и эксперимент с широкими запросами quadtree.

## Приоритеты

| Приоритет | Находка | Статус |
|---|---|---|
| P1 | В npm-пакете отсутствуют цели обоих exports | Воспроизведённая ошибка упаковки |
| P1 | Selection/query и модульные операторы ещё не реализованы | Разрыв между выбранным интерфейсом и кодом |
| P1 | Временной индекс и причинный граф создаются одним модулем | Подтверждено кодом |
| P2 | Tree и Timeline по-разному разрешают заменённые сущности | Подтверждено; оба поведения документированы |
| P2 | Полностью покрытые узлы quadtree можно принимать целиком | Проверенный эксперимент, ещё не production-изменение |
| P2 | В построении Timeline и sorted есть лишние возможности копирования | Кандидаты для замеров |
| P2 | Мало данных о долгоживущих структурах, памяти и GC | Пробел в измерениях |
| P2 | Проверка плотности значительно дороже на Bun | Подтверждено текущим отчётом, не ошибка валидатора |
| P2 | Прямой date-fns-интерфейс пока отсутствует | Запланировано, не реализовано |
| P3 | Readonly не защищает метаданные от изменения в JavaScript | Явный контракт; требует решения для публичного интерфейса |

P1 — закрыть перед обещанием целевого интерфейса или публикацией.
P2 — следующая проработка с проверками и измерениями.
P3 — уточнение интерфейса и его стоимости, без автоматического усложнения.

## 1. Упаковка: exports указывают на отсутствующие файлы

[package.json](../package.json#L7) указывает на dist/src/index.js и .d.ts,
а также dist/src/zod/index.js и .d.ts. Files whitelist и prepack отсутствуют,
dist исключён через [.gitignore](../.gitignore).

npm pack --dry-run включает 67 файлов, 490187 распакованных байт, в том числе
bench, test и references, но ни одну из четырёх целей exports. Это наблюдение
не зависит от наличия локального dist после сборки.

Реальный tarball распакован в node_modules/ts-algo отдельного consumer с
собственным package.json: оба импорта ts-algo и ts-algo/zod дают
ERR_MODULE_NOT_FOUND с отсутствующим файлом в dist/src.

Локальная проверка импорта внутри самого репозитория недостаточна: self-reference
может разрешиться в текущий checkout вместо распакованного пакета.

Рекомендация: files whitelist для dist/src и необходимых материалов пакета,
prepack-сборка, проверка установленных tarball JS и деклараций из отдельного
consumer. Исходники тестов, бенчмарки и теоретические референсы не публиковать
как содержимое runtime-пакета. Package private: true пока предотвращает обычную
публикацию; дефект относится к готовности артефакта, не к уже опубликованному npm.

Lockfile отслеживается Git, npm ci с ним проходит. Проблемы воспроизводимости
установки из-за отсутствующего lockfile не подтверждены.

## 2. Сначала ядро выборок, затем расширение набора структур

[index.ts](../src/index.ts) экспортирует конструкторы всех коллекций.
Query/from/filtered/pipe пока существуют только в [проекте интерфейса](design.md).
Коллекции по-прежнему возвращают объекты с методами; root загружает предметные
модули при обычном ESM-импорте, хотя bundler умеет удалять неиспользуемый код.

Рекомендация: сначала реализовать Selection/from/query на Array/Map/Set/Iterable,
а затем подключать индексы через общий доступ к ссылкам, сущностям и контексту.
В тестах проверить не только правильный результат, но и сохранение branded keys,
сужение после type guard, порядок take/sorted, количество вызовов селекторов,
одноразовые итераторы и отсутствие промежуточного массива на каждый фильтр.
Вывод типов будущего интерфейса был проверен прототипом; готовая реализация и
сужение последовательности шагов этим не доказаны.

PointIndex<Ref> сейчас не сохраняет тип Entity и публичную связь с resolver.
Чтобы within сразу возвращал связанную Selection, нужен общий source binding.
Проверить его lifetime: связь с Map может удерживать сами сущности дольше,
чем индекс, которому нужны только ключи и кеш координат.

## 3. Timeline оплачивает причинность даже без связей

[timeline.ts](../src/timeline.ts#L96) создаёт incoming/effects/causes/pending,
строит массив causal и содержит реализацию всех графовых обходов.
Даже без рёбер присутствуют дополнительные Map и O(n) массив causal.
Весь набор методов создан конструктором; импорт временного поиска не может
удалить возвращаемые им методы обхода графа как независимые функции.

Рекомендация: отдельные temporal index и causal index, связываемые с одним
источником. Сравнить point-only, interval-only и time+causality: построение,
удерживаемая память, размер конкретных импортов. Не заменять методы тонкими
функциями, оставляя прежний конструктор без изменений.

## 4. Владение сущностями: контракт должен быть согласован

[tree.ts](../src/tree.ts#L28) копирует Map записей через snapshotMap.
[Timeline](../src/timeline.ts#L146) сохраняет внешний resolver/Map и читает
текущую сущность. Для одной записи после storage.set с новым объектом rank=2:
Tree продолжает возвращать прежний rank=1, Timeline возвращает rank=2.
Время/связи Timeline при этом остаются первоначальным снимком.

Это не ошибка обхода: оба поведения явно описаны. Но общий query должен иметь
понятный контракт источника, иначе одинаковые выражения читают разные версии
сущностей. Разделить политику чтения сущностей и снимок структурных метаданных.
Если выбираем единый внешний resolver, снимок можно готовить явно нативным
new Map(source), не вводя множество флагов каждой коллекции. Изменение
существующего Tree-контракта делать явно и с тестами замены/удаления записей.

## 5. Quadtree: принимать целиком полностью покрытые узлы

[within](../src/point-index.ts#L128) отбрасывает непересекающиеся узлы, но затем
обходит все дочерние узлы и проверяет координаты каждой возвращаемой точки.
Если bounds полностью покрывает node.bounds, можно сразу добавить ссылки
из его диапазона order[start..end), пропустив дальнейшие проверки координат.

Временный вариант отличается только такой веткой перед обработкой children:

```js
if (node.minX >= bounds.minX && node.maxX <= bounds.maxX &&
    node.minY >= bounds.minY && node.maxY <= bounds.maxY) {
  for (let j = node.start; j < node.end; j++) {
    result.push(references[order[j]]);
  }
  continue;
}
```

Эксперимент: Apple M5, Node 25.8.1/V8 14.1.146.11-node.21, Bun 1.3.14,
100000 равномерных точек [0,1000)². Seed 123, LCG 1664525/1013904223,
координаты последовательно из uint32/2³². Индексы построены вне замера.
3 прогрева, 7 образцов, варианты чередуются через bench/measure; GC перед
образцом вне замера. Результаты сравнивались по отсортированным ID.

| Runtime | Запросы в образце | Исходный, медиана ms | Вариант, медиана ms |
|---|---|---:|---:|
| Node | 64 узких окна 20×20 | 0.1402 | 0.1282 |
| Bun | 64 узких окна 20×20 | 0.1252 | 0.1239 |
| Node | 16 одинаковых окон [250,750]² | 2.7399 | 1.5300 |
| Bun | 16 одинаковых окон [250,750]² | 2.8046 | 0.9749 |
| Node | 8 окон всей области [0,1000]² | 5.3162 | 2.6226 |
| Bun | 8 окон всей области [0,1000]² | 5.2795 | 1.5360 |

На узких окнах диапазоны min/max перекрываются: ускорение не установлено.
Для средних/широких окон результат перспективен, но это один workload и один
процесс на runtime. Перед внедрением добавить сравнения на границах, совпадающих
точках, вырожденных областях и Map-источнике, измерить регрессии узких запросов
и стоимость JS. Within сейчас не обещает порядок; вариант его может изменить.
Для будущей Selection это требование следует явно сохранить или пересмотреть.
Сложность возвращения k ссылок остаётся как минимум O(k).

## 6. Буферы построения и сортировки

В [Timeline](../src/timeline.ts#L123) исходные refs/starts/ends затем копируются
в хронологический порядок через sorted; повторяются positions.get при
сортировке и сборке. Общий sorted добавляет свои values/order/result.
Кандидат: сортировать исходные числовые позиции напрямую и собирать итоговые
буферы за один проход, сохраняя устойчивость и идентичность ссылок.
Это внутренняя оптимизация конструирования, не новый публичный алгоритм.

[sorted](../src/sorted.ts#L47) при n > 1 выделяет 3 массива для Array, 4 для Map/прочих
Iterable. Кеширование значений даёт один вызов дорогого селектора, но для
дешёвого селектора обычная нативная сортировка может быть выгоднее по памяти.
Проверить упаковку индексов в TypedArray, обычные массивы и повторное использование
локальных буферов — без общего глобального scratch-буфера и без обещания
универсального ускорения. Измерить отдельно время и retained/peak memory.

Не подменять общий sorted прямым sort массива ссылок без проверки контракта:
native sort обрабатывает undefined-элементы особо. Воспроизведение:
sorted([undefined, "a"], ref => ref === undefined ? 0 : 1, (a,b) => a-b)
возвращает [undefined, "a"], прямой toSorted по той же проекции — ["a", undefined].
Сортировка индексов сейчас корректно сохраняет заданную семантику ссылок.

## 7. Долгоживущие очереди, память и методика

[Queue](../src/queue.ts#L23) создаёт новый пустой массив при каждом полном
опустошении и иногда копирует хвост при compaction. Peek читает items[head]
также в пустом состоянии. Кандидаты: повторное использование буфера и явная
проверка пустоты peek; влияние на JIT и GC сначала измерить.

[Deque](../src/deque.ts#L17) удваивает кольцевой буфер и сохраняет его длину
после извлечения всех элементов; clear возвращает буфер к 16 слотам.
Ссылки на извлечённые сущности освобождаются. Это не утечка сущностей, но
high-water capacity может стоить памяти после большого всплеска.
Нужен замер роста → опустошения → небольшого потока; не вводить автоматическое
уменьшение без проверки циклических нагрузок.

Текущие sequence-бенчмарки преимущественно строят и полностью опустошают
коллекцию. Добавить enqueue/dequeue в течение длительного потока, удерживаемые
node handles, редкие массовые правки, рост/сжатие, latency при compaction.
Map-based linked list пока гипотеза: замерить против узлов, учитывая отдельные
occurrence IDs для повторов и стоимость next/previous/ownership-проверок.

В [measure](../bench/measure.ts#L18) сохраняются median/min/max, но исходные
образцы из общего helper теряются. Большинство отчётов не измеряет peak/retained
heap, allocation rate и браузеры. Принудительный GC перед образцами полезен
для повторяемости, но не заменяет замер естественного GC и p95 задержек.
Добавить raw samples, сценарии end-to-end и Chrome/Safari перед общими
обещаниями производительности фронтенда. Bundle smoke уже проверяет готовый JS,
но нужен дополнительно отдельный consumer tarball и ещё один bundler.

## 8. Плотность и Zod: стоимость контракта

При 100000 элементах текущий [Bun-отчёт](validation-results-bun.md) показывает
5.2709 ms для isDenseArray и 6.1199 ms для denseArray с проверкой элементов;
[Node](validation-results-node.md) — 0.3812 и 0.8452 ms соответственно.
Это разные движки и разная работа вариантов, не доказательство универсальной
неэффективности валидатора. Гарантировать собственный индекс в каждой позиции
требует полного прохода в худшем случае.

Не ослаблять проверку до every/forEach или принимать унаследованные индексы
ради цифры в бенчмарке. Проверять при приёме данных, не при каждом сравнении.
IsDenseArray не копирует сущности; denseArray запускает парсинг элементов,
поэтому z.object может заменить объект клоном. Схему проверки выбирать с
учётом требуемой идентичности. Опциональный zod-entry уже изолирован от core.

## 9. Время и runtime readonly

Date-fns пока выбран в проекте, но его публичные Date/Interval-входы не
реализованы. При миграции проверить Invalid Date, полуоткрытые границы,
нулевые интервалы, явный разбор строк, Date-подклассы, DST/часовые пояса и
мутацию Date после построения. Числовые метаданные остаются кешированными; календарные
операции и преобразования выполняются вне горячего поиска.

Readonly roots/children/causes защищены типами, но наружу возвращаются
сами внутренние массивы. Это задокументированный контракт, не обещание
runtime-заморозки. Для публичного JS-интерфейса выбрать: закрытые итераторы,
копии или однократный freeze метаданных. Копия на каждом чтении может нарушить
требования к памяти; freeze имеет стоимость построения/представления.

## Последовательность работы

1. Исправить npm-артефакт и добавить проверку отдельного consumer.
2. Реализовать Selection/from/query и согласовать чтение сущностей.
3. Отделить temporal index от причинного графа и подключить date-fns-входы.
4. Внедрить проверенную quadtree-гипотезу после расширения differential tests.
5. Измерить и уменьшить временные буферы Timeline; расширить memory/GC workloads.
6. Остальные микрооптимизации выполнять по замерам, не по форме TS-кода.

Не переносить Quicksort обратно в публичный интерфейс, не добавлять глобальные
буферы и не превращать Result/Optional в обёртку каждого элемента без задачи.
Документ фиксирует состояние проверяемого commit; архитектура остаётся
авторитетно описанной в design.md, этот отчёт не заменяет её.
