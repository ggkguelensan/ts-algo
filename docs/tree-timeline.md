# Дерево и связанные события

Оба модуля принимают `ReadonlyMap<Key, Entity>`, сохраняют сущности и строят
статический снимок состава и связей. Селекторы не должны изменять источник.
Результат тоже реализует `ReadonlyMap`: существующие `sortedReferences` и
`pointIndex` получают сущности непосредственно, без новой перегрузки и внешнего
`Map.get`. Итерация Map возвращает пары `[key, entity]`, `keys()` — ключи.

## Дерево

```ts
import { tree, sortedReferences } from "../src/index.js";

type Item = Readonly<{ parentId: string | null; title: string }>;
const storage = new Map<string, Item>([
  ["catalog", { parentId: null, title: "Каталог" }],
  ["phones", { parentId: "catalog", title: "Телефоны" }],
  ["books", { parentId: "catalog", title: "Книги" }],
]);
const catalog = tree(storage, { parent: item => item.parentId });
catalog.roots;                    // ["catalog"]
catalog.children("catalog");     // ["phones", "books"]
catalog.parent("books");         // "catalog"
[...catalog.subtree("catalog")];  // ["catalog", "phones", "books"]
[...catalog.ancestors("books")];  // ["catalog"]

// Новый вид: сортируем соседей, сохраняем иерархию.
const ordered = catalog.sortBy(item => item.title, (a, b) => a.localeCompare(b));
ordered.children("catalog"); // ["books", "phones"]

// Общий рейтинг: плоский массив ключей всех узлов.
const ranking = sortedReferences(catalog, item => item.title, (a, b) => a.localeCompare(b));
```

Формально это лес: несколько корней допустимы. Корни и дети сначала идут в
порядке источника. `keys()` выполняет preorder: узел перед потомками. `sortBy`
устойчиво сортирует корни и каждую группу детей; исходный вид и сущности не
меняются. Для групп из одного узла селектор не вызывается; для остальных — один
раз на узел. Сущности не оборачиваются в объекты узлов и не получают поле children.

`null`/`undefined` в parent означают корень. Ключи дерева поэтому должны быть
non-nullish; строки, числа и объекты подходят. Отсутствующий родитель, цикл и
обращение к отсутствующему узлу — RangeError. `parent(root)` возвращает undefined,
`children(leaf)` — пустой readonly-массив. Структурные массивы доступны только для
чтения по контракту: runtime не замораживает их; изменять их через обход типов нельзя.

Обходы и проверка циклов итеративны; глубина 20 000 проверяется тестом без
переполнения стека. Первый вход — нормализованный Map с селектором родителя.
Для генератора ancestors проверка ключа выполняется при начале обхода.
Вложенные объекты с children пока требуют адаптера: автоматическое распознавание
нескольких форм дерева не реализовано.

При обычной средней стоимости Map-операций построение и полный обход O(n).
Сортировка требует суммы сортировок групп, не хуже O(n log n) в измеренных
движках, плюс O(n) подготовка. Предки — O(h), поддерево — O(k). Новый вид разделяет
Map сущностей и родителей с исходным; порядок корней и группы детей хранятся
отдельно. Это бизнес-иерархия, не сбалансированное дерево поиска.

## Временная линия

События-точки организованы в три индекса:

- Отсортированные ключи + кеш времени: диапазон через два бинарных поиска.
- Map владельцев: для каждого владельца — позиции в общем временном порядке.
- Причинный DAG: входящие/исходящие связи и подготовленный топологический порядок.

```ts
import { timeline } from "../src/index.js";

type Event = Readonly<{ at: number; ownerId: string; causedBy: readonly string[] }>;
const storage = new Map<string, Event>([
  ["order", { at: 1000, ownerId: "customer", causedBy: [] }],
  ["payment", { at: 2000, ownerId: "customer", causedBy: ["order"] }],
  ["shipment", { at: 3000, ownerId: "warehouse", causedBy: ["payment"] }],
]);
const events = timeline(storage, {
  at: event => event.at,
  owner: event => event.ownerId,
  causes: event => event.causedBy,
});
events.between(1000, 3000); // ["order", "payment"]
events.forOwner("customer").between(0, 4000); // ["order", "payment"]
events.causesOf("shipment"); // ["payment"]
events.effectsOf("order"); // ["payment"]
events.ancestors("shipment"); // ["payment", "order"]
events.descendants("order"); // ["payment", "shipment"]
events.causalOrder(); // ["order", "payment", "shipment"]
```

Связи могут проходить между разными владельцами. Владелец — группировка, а не
причинность. У события может быть несколько причин: например, отгрузка после
оплаты и одобрения. Поэтому DAG не моделируем одним parentId дерева. Если
владельцы образуют иерархию, для неё отдельно используем tree; события не
дублируются под каждым владельцем и причиной.

Владелец сейчас один на событие; идентичность определяется Map. owner и causes
необязательны. Без owner запрос forOwner запрещён типом; без causes причинный
порядок совпадает с временным. Неизвестный владелец даёт пустое окно. Неизвестный
ключ в операциях причинности — RangeError. Ключи событий могут быть null/undefined:
список причин не использует их как маркер отсутствия. Повторные причины удаляются.

`between` возвращает события в `[start, end)`, по возрастанию at, сохраняя порядок
источника при равенстве. Пустое окно допустимо. Время/границы — конечные number в
одних единицах вызывающего кода; неверные значения и start > end — RangeError.
Модуль не преобразует даты и не выбирает часовой пояс. `get` возвращает исходную
сущность; изменение её at не обновляет индекс. После изменений состава, времени,
владельцев или связей нужно построить новый снимок.

Временной и причинный порядок различаются. Из-за несогласованных часов метка
причины может оказаться позже следствия. Такие данные допустимы; `causalOrder`
ставит причины перед следствиями. Алгоритм Kahn использует FIFO готовых узлов:
начальные узлы идут по времени, связи — по порядку источника. Это детерминированный
топологический порядок, не выбор самого раннего доступного узла на каждом шаге.
Отсутствующие причины и циклы — RangeError. Другой пример топологического обхода:
[NetworkX](https://github.com/networkx/networkx/blob/main/networkx/algorithms/dag.py).

`ancestors`/`descendants` возвращают уникальные ключи обходом в ширину: ближайшие
связи сначала, стартовое событие не включено. Это порядок обхода графа, не
хронологическая сортировка. Массивы прямых связей readonly по контракту; изменять
их нельзя. Подготовительные Map времени/владельцев и селекторы отделены от
замыканий запросов; внутри запросов данные повторно не извлекаются из сущностей.

При обычной средней стоимости Map-операций построение O(n log n + r), хранение
O(n + e), r — число переданных причинных ссылок, e — число уникальных связей.
Повторы тоже требуют обработки при построении. Диапазон — O(log n + k); для
владельца — O(log m + k), m — число его событий. Причинный обход — O(v + e) для
достижимой части, causalOrder возвращает копию подготовленного массива O(n).
Селекторы вызываются один раз на событие; Iterable причин должен быть конечным.

Это **статический индекс событий-точек**, не interval index и не структура с
быстрыми вставками. Поиск по at не находит все пересечения длительных start/end
событий. Для длительностей нужен отдельный контракт пересечения; для частых
вставок/редактирования — отдельные замеры и выбор структуры. Нынешний вариант
подходит для загруженной истории, аналитики и повторных запросов к снимку.

## Стоимость

```sh
npm run bench:hierarchy-time
npm run bench:hierarchy-time:bun
npm run bench:bundle
```

[Node/V8](hierarchy-time-results-node.md), [Bun/JavaScriptCore](hierarchy-time-results-bun.md),
[размер модулей](bundle-results.md). Проверяются 1 000, 10 000, 100 000 событий,
случайные/отсортированные/равные времена, владельцы и причинная цепочка; деревья
широкие и глубокие. Native baseline использует уже упорядоченные ключи и filter,
без новой сортировки на каждый запрос. Есть также filter по кешированным времени
и владельцам, чтобы отделить эффект индекса от кеширования селекторов.
Timeline-build включает владельцев и граф; native-sort этого не делает.
GC перед каждым образцом вызывается вне таймера; GC внутри вызова входит во время.
Есть построение вместе с запросами и единственный запрос. При редком поиске
индекс может не окупиться; большой результат требует записи всех k ключей.
Динамические обновления, браузеры и peak heap пока не измеряем.
